SPEC_NAME: Investment Morning Report Audit Ledger  
SPEC_VERSION: 1.1  
STATUS: FROZEN  
EFFECTIVE_FROM: 2026-08-19  
SUPERSEDES: Audit Ledger v1.0  
RETENTION_POLICY: PERMANENT  
AUTHORITY_ROLE: Protocol Authority  
  
============================================================  
1. PURPOSE  
============================================================  
Audit Ledger v1.1 在 v1.0“判断可审计”的基础上，增加“研究逻辑可重建”能力。  
  
核心目标：  
- 保存当时正式判断了什么；  
- 保存足够的当时研究状态，使月度复盘能够重建为什么形成该判断；  
- 保存关键证据与当时假定的传导链，以便事后定位哪一环走通、哪一环失效；  
- 不保存整篇晨报，不追求无损历史；目标是 Research-sufficient History（足以重建研究过程的历史）。  
  
原则：  
Memory != Audit Log  
Conversation History != Prediction Record Authority  
Prediction Creation != Evaluation  
Research Snapshot != Morning Report Backup  
Reality must be re-verified from official/authoritative sources at evaluation time.  
  
============================================================  
2. AUTHORITY & VERSIONING  
============================================================  
Protocol Authority Subject:  
[INV-AUDIT][SPEC] Audit Ledger v1.1  
  
v1.0 永久保留且不得修改。v1.1 自 EFFECTIVE_FROM 起适用于新创建的 Daily Ledger；不得迁移、补写、重写或“升级”既有 v1.0 Daily Ledger。  
  
月报/读取器必须向后兼容：  
- SPEC_VERSION: Audit Ledger v1.0  
- SPEC_VERSION: Audit Ledger v1.1  
  
对 v1.0 记录缺少 Research Logic Snapshot 属于正常 schema 差异，不得标记为数据缺失。  
  
============================================================  
3. STORAGE & IMMUTABILITY  
============================================================  
Daily Ledger 使用 Gmail Draft，Subject 严格为：  
[INV-AUDIT][DAILY] YYYY-MM-DD  
  
每个自然日最多一封正式 Daily Ledger。  
  
SPEC 与 Daily 均遵循 write-once-read-many：  
允许 READ / SEARCH；  
禁止 UPDATE / SEND / DELETE / REPLACE / overwrite。  
  
旧判断发生变化时，只能通过后续新事件引用旧 ID 表达，不得回写旧记录。  
  
============================================================  
4. EVENT-DRIVEN WRITES  
============================================================  
只有出现至少一种正式事件时才允许创建 Daily Ledger：  
- BASELINE_CHANGED  
- BASELINE_CONFIDENCE_CHANGED  
- FORECAST_CREATED  
- FORECAST_CONFIDENCE_CHANGED  
- HYPOTHESIS_CREATED  
- HYPOTHESIS_STATUS_CHANGED  
- METHOD_CHANGED  
  
仅重复旧判断、普通新闻、常规行情、无正式方向性预测时不创建 Draft。  
不得创建 NO_CHANGE 事件。  
  
============================================================  
5. TIME AUTHORITY  
============================================================  
每封 Daily Ledger 至少包含：  
SCHEMA_VERSION: 1.1  
SPEC_VERSION: Audit Ledger v1.1  
EVENT_DATE: YYYY-MM-DD  
TASK_SCHEDULED_FOR: YYYY-MM-DDT08:00:00+08:00  
LEDGER_CREATED_AT: 当前实际 Asia/Shanghai 时间；无法可靠取得时写 UNKNOWN  
  
Gmail UI 时间、MIME Date、autosave 时间不是语义上的预测创建时间 Authority。  
  
============================================================

============================================================  
FORECAST_CREATED 必须完整预注册：  
EVENT  
ID  
 date  
 domain  
 horizon  
 judgment  
 direction  
 confidence  
 validation  
 invalidation  
 evaluation_window  
 evaluation_rule  
  
Forecast ID 永久唯一，建议格式：  
YYYYMMDD-DOMAIN-seq  
  
不满足方向、时间尺度、验证/失效条件、评价窗口和事前评价规则的判断，不得强行登记为正式 Forecast。  
  
============================================================  
7. RESEARCH LOGIC SNAPSHOT  
============================================================  
以下事件必须附研究逻辑快照：  
- FORECAST_CREATED  
- BASELINE_CHANGED  
- HYPOTHESIS_CREATED  
- METHOD_CHANGED  
  
HYPOTHESIS_STATUS_CHANGED 在发生重大状态变化时必须附快照，例如：  
OPEN -> CONFIRMED  
OPEN -> REJECTED  
或出现足以改变核心因果机制的新证据。  
  
FORECAST_CONFIDENCE_CHANGED 与 BASELINE_CONFIDENCE_CHANGED 默认只需简短 reason；若新证据同时改变核心因果链，可附 Snapshot。  
  
研究逻辑快照由以下字段组成：  
  
RATIONALE_SNAPSHOT:  
回答“为什么此刻形成或改变这个判断”。只保存决定性逻辑，不复述晨报全文。  
普通事件原则上不超过约300中文字；重大框架/方法变化可放宽至约500中文字。  
  
EVIDENCE_SNAPSHOT:  
保存当时真正改变判断的2—5项关键证据。  
不得复制所有新闻；必须优先保存具有判别力的信息。  
只允许写入创建时已经知道的证据。  
  
CAUSAL_CHAIN:  
记录当时假定的主要传导机制，通常3—7个节点，例如：  
A -> B -> C -> D  
如果不存在真正的因果链，写 NOT_APPLICABLE。  
如果当时链条未知，不得事后补齐，应保留 UNKNOWN_TRANSMISSION。  
  
SOURCE_POINTERS:  
保存1—5个轻量来源定位信息，例如：  
- BLS / Employment Situation / 2026-08-07  
- Federal Reserve / FOMC Statement / 2026-07-29  
- Company IR / Q2 2026 Earnings  
不要求保存长URL或全文。月底仍必须重新获取 Reality Authority。  
  
CHANGE_TRIGGER:  
仅在旧状态明确变化时填写，回答“什么新证据使旧看法发生变化”。  
建议同时写 previous_view 与 current_view。  
  
============================================================  
8. SNAPSHOT PROHIBITIONS  
============================================================  
禁止：  
9) 把晨报正文复制进 Snapshot；  
10) 写入事后才知道的证据；  
11) 修改旧 Snapshot；  
12) 为了故事完整而事后补齐因果链；  
13) 为每个普通新闻或重复观点创建 Snapshot。  
  
若 Snapshot 持续膨胀到接近晨报全文，应主动压缩，只保留研究骨架。  
  
============================================================  
14. BASELINE / HYPOTHESIS / METHOD  
============================================================  
BASELINE_CHANGED：记录 previous/current baseline、confidence、trigger，并必须附 Research Logic Snapshot。  
  
BASELINE_CONFIDENCE_CHANGED：基线方向未变，仅证据强弱改变；默认只需 reason。  
  
HYPOTHESIS_CREATED：用于解释机制，不计入预测命中率；必须附 Snapshot。  
  
HYPOTHESIS_STATUS_CHANGED：状态可为 OPEN / CONFIRMED / STRENGTHENED / WEAKENED / REJECTED。重大状态变化必须附 Snapshot。  
  
METHOD_CHANGED：记录研究方法、信号权重、框架或评价方式发生的正式改变；必须附 Snapshot，不进入预测胜率。  
  
============================================================  
15. MONTHLY RECONSTRUCTION  
============================================================  
月报首先读取目标期间 Daily Ledger，按 SPEC_VERSION 解析。  
  
重建：  
- Forecast List  
- Baseline Timeline  
- Confidence Changes  
- Hypothesis Timeline  
- Method Changes  
- Rationale Snapshots  
- Evidence at Creation  
- Causal Chains  
- Change Triggers  
  
随后重新获取 Reality Authority，再进行评价。  
  
月报必须区分：  
Prediction Authority = Daily Ledger  
Reasoning-at-Creation Authority = v1.1 Research Logic Snapshot  
Reality Authority = official/authoritative current or historical sources  
Evaluation Authority = monthly review / user-confirmed formal monthly report  
  
月报评价除方向/时点/幅度外，还应尽量判断：  
- 原始事实假设是否错误；  
- 传导关系是否错误；  
- CAUSAL_CHAIN 在哪一环走断；  
- 当时是否遗漏关键变量；  
- 是否存在政策反应、估值、市场与基本面阶段性脱钩等问题。  
  
============================================================  
11. EVALUATION RESULTS  
============================================================  
正式预测结果：  
- CORRECT  
- PARTIAL_TIMING_OR_MAGNITUDE  
- WRONG_DIRECTION  
- NOT_YET_VERIFIABLE  
  
错误类型至少可使用：  
- DATA_ERROR  
- TRANSMISSION_ERROR  
- TIMING_ERROR  
- MAGNITUDE_ERROR  
- OMITTED_VARIABLE  
- POLICY_REACTION_ERROR  
- MARKET_FUNDAMENTAL_DECOUPLING  
- UNPREDICTABLE_EVENT  
  
不得用“突发事件”作为停止分析的理由；仍需判断该风险是否本应获得更高事前权重。  
  
============================================================  
12. IDEMPOTENCY & DUPLICATE HANDLING  
============================================================  
写入前必须验证 v1.1 SPEC Authority 唯一性。  
  
Subject 严格为：  
[INV-AUDIT][SPEC] Audit Ledger v1.1  
  
匹配数：  
0 -> AUDIT_SPEC_UNAVAILABLE，不写 Daily；  
1 -> 正常读取；  
>1 -> AUDIT_SPEC_DUPLICATE，fail-closed，不得任意选择或自我 canonicalize。  
  
创建 Daily 前精确搜索：  
[INV-AUDIT][DAILY] YYYY-MM-DD  
  
0 -> 若有正式事件可创建；  
1 -> AUDIT_LEDGER_ALREADY_EXISTS，不修改、不再创建；  
>1 -> AUDIT_LEDGER_DUPLICATE，不修改、不删除、不合并，等待人工处理。  
  
============================================================  
13. FAILURE HANDLING  
============================================================  
Audit 持久化失败不得导致晨报正文失败。  
  
失败时：  
- 不得声称已保存；  
- 不得通过修改旧 Draft 补救；  
- 报告 AUDIT_PERSISTENCE_FAILED 与简短原因。  
  
回填如未来被允许，也必须保留真实回填时间，不能伪装成原始实时写入。  
  
============================================================  
14. RETENTION & MIGRATION  
============================================================  
SPEC: PERMANENT  
DAILY: PERMANENT  
未来 MONTHLY_FINAL: PERMANENT  
  
正式 Authority 不设计自动删除机制。  
如果 Gmail 未来不再适合：  
迁移 -> 核验数量/ID/内容完整性 -> 激活新 Authority -> 用户明确批准 -> 再退休旧存储。  
  
设计迁移机制，不设计自动删除机制。  
  
============================================================  
15. DESIGN PRINCIPLE  
============================================================  
v1.0：保证“判断可审计”。  
v1.1：在此基础上保证“研究逻辑可重建”。  
  
保存的不是所有信息，而是足以回答以下问题的研究骨架：  
- 当时正式判断了什么？  
- 为什么这么判断？  
- 哪几项证据真正改变了观点？  
- 当时认为如何传导？  
- 后来真实发生了什么？  
- 哪一环走通或走断？  
- 下一次应如何改进方法？
