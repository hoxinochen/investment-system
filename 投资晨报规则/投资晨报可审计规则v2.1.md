============================================================  
1. PURPOSE  
============================================================  
  
本 SPEC 定义投资晨报正式研究事件的持久化协议。  
  
Daily Ledger 用于保存：  
2. 可审计的正式 Forecast / Baseline / Hypothesis / Confidence / Method 事件；  
3. 当时足以重建研究逻辑的最小 Research Logic Snapshot；  
4. 在月度 Handoff 之间发生、且需要影响后续晨报的正式 Research Priority（研究优先级）变化。  
  
Daily Ledger 不是晨报全文备份，不保存普通新闻、常规行情、无变化状态或纯粹的研究过程噪音。  
  
============================================================  
5. STORAGE & IMMUTABILITY  
============================================================  
  
Daily Ledger 使用 Gmail Draft，Subject 严格为：  
[INV-AUDIT][DAILY] YYYY-MM-DD  
  
每个自然日最多一封正式 Daily Ledger。  
  
SPEC 与 Daily Ledger 均为 write-once-read-many（WORM）。  
允许：READ / SEARCH。  
禁止：UPDATE / SEND / DELETE / REPLACE / OVERWRITE。  
  
冻结后的历史 SPEC 与 Daily Ledger 不得修改、补写、迁移或重解释。  
任何后续变化必须通过新的 Daily Event 表达，并在需要时引用旧 Event ID。  
  
============================================================  
6. FORMAL EVENT TYPES  
============================================================  
  
允许的正式事件类型：  
- BASELINE_CHANGED  
- BASELINE_CONFIDENCE_CHANGED  
- FORECAST_CREATED  
- FORECAST_CONFIDENCE_CHANGED  
- HYPOTHESIS_CREATED  
- HYPOTHESIS_STATUS_CHANGED  
- METHOD_CHANGED  
- RESEARCH_PRIORITY_CHANGED  
  
仅重复旧判断、普通新闻、常规行情、无正式方向性判断、无正式研究状态变化时，不创建事件。  
不得创建 NO_CHANGE / NO_DRIFT / DRIFT_CHECKED 等事件。  
  
Research Drift Check（研究漂移检查）本身属于运行时行为，不是持久化事件；只有检查后真的改变后续研究注意力分配时，才允许创建 RESEARCH_PRIORITY_CHANGED。  
  
============================================================  
4. TIME AUTHORITY  
============================================================  
  
每封正式 Daily Ledger 至少包含：  
  
SCHEMA_VERSION: 2.0  
SPEC_VERSION: Audit Ledger v2.1  
EVENT_DATE: YYYY-MM-DD  
TASK_SCHEDULED_FOR: YYYY-MM-DDT08:00:00+08:00  
LEDGER_CREATED_AT: 当前实际 Asia/Shanghai 时间；无法可靠取得时写 UNKNOWN  
  
Gmail UI 时间、MIME Date、Draft autosave 时间不是语义上的事件创建时间 Authority。  
  
历史 Ledger 始终按其自身 SPEC_VERSION 解释，不得使用 v2.0 重新解释 v1.x 历史记录。  
  
============================================================  
5. FORECAST_CREATED  
============================================================  
  
正式 Forecast 创建时至少包含：  
  
EVENT: FORECAST_CREATED  
ID:  
date:  
domain:  
horizon:  
judgment:  
direction:  
confidence:  
validation:  
invalidation:  
evaluation_window:  
evaluation_rule:  
  
Forecast 必须事前定义评价窗口和可复核评价规则。  
Prediction Authority 永远属于原始 Forecast 记录；后续月报、Handoff 或其他事件不得重写原 Forecast 的 judgment、direction、confidence、evaluation_rule 或 invalidation。  
  
FORECAST_CREATED 必须附 Research Logic Snapshot。  
  
============================================================  
6. FORECAST_CONFIDENCE_CHANGED  
============================================================  
  
用于同一 Forecast 在评价窗口内因新增证据发生正式置信度变化。  
  
至少包含：  
EVENT: FORECAST_CONFIDENCE_CHANGED  
ID:  
ref_forecast_id:  
old_confidence:  
new_confidence:  
reason:  
  
不得借置信度变化重写原 Forecast 方向或判断。  
若新增证据已经改变原 Forecast 的核心方向，应按 SPEC 规则创建新的正式 Forecast，而不是覆盖旧记录。  
  
置信度变化默认只需保存简短 reason；若核心因果机制发生实质变化，则附 Research Logic Snapshot。  
  
============================================================  
7. BASELINE EVENTS  
============================================================  
  
BASELINE_CHANGED：现实世界模型的核心方向或状态发生正式变化。  
BASELINE_CONFIDENCE_CHANGED：Baseline 方向未改变，但置信度发生正式变化。  
  
BASELINE_CHANGED 必须附 Research Logic Snapshot。  
BASELINE_CONFIDENCE_CHANGED 默认保存简短原因；若核心机制变化，则附 Snapshot。  
  
不得因单个数据点、短期行情或一次事件结果轻易创建 BASELINE_CHANGED。  
  
============================================================  
8. HYPOTHESIS EVENTS  
============================================================  
  
HYPOTHESIS_CREATED 用于提出尚待进一步证伪/验证的正式研究假说，必须附 Research Logic Snapshot。  
  
HYPOTHESIS_STATUS_CHANGED 用于已有假说发生重要状态变化，例如：  
OPEN -> STRENGTHENED  
OPEN -> WEAKENED  
OPEN -> REJECTED  
STRENGTHENED -> WEAKENED  
等。  
  
若只是轻微证据增减，不要求机械创建事件；只有足以改变后续研究解释或验证重点时才记录。  
重大状态或核心机制变化时必须附 Research Logic Snapshot。  
  
============================================================  
9. METHOD_CHANGED  
============================================================  
  
METHOD_CHANGED 只用于正式研究方法、评价规则、数据处理规则、预测生成规则或研究治理方法发生变化。  
  
它描述“我们如何研究”的改变，不描述现实世界、某个 Forecast 或某个 Hypothesis 的变化。  
  
METHOD_CHANGED 必须附 Research Logic Snapshot。  
同一方法变化不得在后续 Daily Ledger 重复登记。  
  
============================================================  
10. RESEARCH_PRIORITY_CHANGED  
============================================================  
  
RESEARCH_PRIORITY_CHANGED 用于记录：  
在 Monthly Handoff 之间，由 Research Drift Check、持续 Residual Evidence（残余证据）、Cross-Market Anomaly（跨市场异常）、长期覆盖不足或其他明确研究证据触发的正式研究注意力重新分配。  
  
它表达的是：  
“未来若干晨报应该提高、降低、加入、移除或重新平衡哪些研究主题的注意力。”  
  
它不是：  
- Baseline 变化；  
- Forecast 创建或修正；  
- Hypothesis 状态变化；  
- Method 变化；  
- 单日新闻重要性排序；  
- 普通 Watchlist。  
  
只有当优先级变化预计影响当前晨报之后的后续研究，才允许创建。  
仅仅发现一个新主题、当天临时关注一个事件、执行了 Drift Check 但未改变研究优先级，都不得创建该事件。  
  
正式事件至少包含：

EVENT: RESEARCH_PRIORITY_CHANGED
ID:
date:
topic_key:
action: ADD / RAISE / MAINTAIN / LOWER / EVENT_TRIGGER_ONLY / REFOCUS / DROP
reason:
review_window:

按动作需要补充 focus_on、stop_researching、trigger_condition 或 reentry_condition。
同一 topic_key 在 Event Replay Boundary 之后的更晚 Daily Event 覆盖 Active Handoff 快照中的初始 Directive，但不得修改旧 Handoff。

历史 v1.x 事件兼容读取：
- REMOVE 解释为 DROP；
- REBALANCE 只作为历史动作读取；新记录必须拆成一个或多个带 topic_key 的明确动作。

RESEARCH_PRIORITY_CHANGED 必须附 Research Logic Snapshot。  
  
review_window 用于规定下一次应重新检查该优先级的时间范围，例如 7D、14D 或明确日期区间。review_window 不是自动失效时间；若复核后优先级需要降低、移除或再次提高，应创建新的 RESEARCH_PRIORITY_CHANGED 事件。若复核后状态不变，不创建 NO_CHANGE 事件。  
  
优先级事件不得覆盖 Monthly Handoff。当前 Research Priority 应按：  
Latest Valid Handoff 中的 RESEARCH_PRIORITY_DIRECTIVES  
+ Handoff Event Replay Boundary 之后、截至任务开始前的 RESEARCH_PRIORITY_CHANGED  
按时间顺序重建。  
  
后续优先级事件可以引用旧 ID，但不得修改旧事件。  
  
============================================================  
11. RESEARCH LOGIC SNAPSHOT  
============================================================  
  
以下事件默认必须保存 Research Logic Snapshot：  
- FORECAST_CREATED  
- BASELINE_CHANGED  
- HYPOTHESIS_CREATED  
- METHOD_CHANGED  
- RESEARCH_PRIORITY_CHANGED  
  
HYPOTHESIS_STATUS_CHANGED 在重大状态/机制变化时必须保存。  
FORECAST_CONFIDENCE_CHANGED / BASELINE_CONFIDENCE_CHANGED 在核心因果机制变化时保存。  
  
Snapshot 结构：  
  
RATIONALE_SNAPSHOT:  
- 保存事件发生当时的关键研究理由。  
  
EVIDENCE_SNAPSHOT:  
- 2—5项事件创建时已经知道、且对判断具有决定性的证据。  
- 禁止加入事后才出现的数据。  
  
CAUSAL_CHAIN:  
- 3—7个关键节点；若确实不存在可用传导链，写 NOT_APPLICABLE 或 UNKNOWN_TRANSMISSION。  
  
SOURCE_POINTERS:  
- 1—5个轻量来源定位，例如：  
  Bureau of Labor Statistics / Employment Situation / 2026-08-07  
  Federal Reserve / FOMC Statement / 2026-07-29  
  Company IR / Q2 2026 Earnings  
- 不要求保存长 URL 或全文。  
- 月底 Reality Authority 仍必须重新获取。  
  
CHANGE_TRIGGER:  
- 仅当事件明确描述旧状态为何发生变化时填写。  
- 新建 Forecast / Hypothesis 若无旧状态可变更，可以省略。  
  
Snapshot 只保存足以重建研究逻辑的骨架。  
禁止复制晨报全文；禁止写入事后证据；禁止补齐当时未知的因果链。  
  
============================================================  
12. CURRENT STATE RECONSTRUCTION  
============================================================  
  
Current Research State 在任意时间 T 应通过：  
  
Latest Valid FROZEN Handoff with VALID_FROM <= T  
+ 该 Handoff Event Replay Boundary 之后、T 之前已经存在的相关 Daily Ledger Events  
  
按语义时间顺序重建。  

Event Replay Boundary：Handoff 存在 `SNAPSHOT_CUTOFF` 时使用该时间；仅对历史旧 Handoff 缺少该字段时回退使用 `VALID_FROM`。`VALID_FROM` 决定快照何时激活，`SNAPSHOT_CUTOFF` 决定哪些旧事件已经被快照吸收，二者不得混用。
  
可改变当前研究状态的事件包括：  
- BASELINE_CHANGED  
- BASELINE_CONFIDENCE_CHANGED  
- FORECAST_CREATED  
- FORECAST_CONFIDENCE_CHANGED  
- HYPOTHESIS_CREATED  
- HYPOTHESIS_STATUS_CHANGED  
- METHOD_CHANGED  
- RESEARCH_PRIORITY_CHANGED  
  
历史 Daily Ledger 永远按其自身 SPEC_VERSION 解释。  
  
============================================================  
13. DUPLICATE & DAILY WRITE RULE  
============================================================  
  
创建 Daily Ledger 前，必须完成下文 Draft-native retrieval 的完整查重，并精确核验 `[INV-AUDIT][DAILY] YYYY-MM-DD` 并检查实际 Subject：  
- 经完整 Draft-native 查重确认为 0封：且存在至少一个正式事件时，才可创建；  
- 1封：不得再创建，报告 ALREADY_EXISTS；  
- 多于1封：不得修改、合并或创建新记录，报告 DUPLICATE。  
  
同一自然日的多个正式事件写入同一封 Daily Ledger。  
  
============================================================  
14. FAILURE HANDLING  
============================================================  
  
SPEC 搜索、读取、权限或 Gmail 持久化失败，不得阻止晨报正文生成。  
不得假装已经保存。  
不得通过修改旧 Daily Ledger 补救。  
不得用聊天记忆替代当前有效 SPEC。

16. DESIGN PRINCIPLE  
============================================================  
  
只持久化真正改变研究状态的事件。  
  
Reality Change -> Baseline Event  
Forecast Change -> Forecast Event  
Hypothesis Change -> Hypothesis Event  
Research Method Change -> Method Event  
Research Attention Change -> Research Priority Event  
  
Research Drift Check 是运行时控制回路；只有发生 Attention Allocation（注意力分配）变化时才进入 Ledger。  
  
目标是让：  
Monthly Handoff = 慢速研究快照  
Daily Ledger = 快速状态事件流  
Morning Report = 当前现实研究与执行界面  
Monthly Review = 深度自我审计与世界模型校准  
  
共同组成可验证、可回溯、不过度持久化噪音的研究系统。

============================================================
DRAFT-NATIVE RETRIEVAL — Gmail Draft 检索协议
============================================================
适用于本制品职责范围内所有存放在 Gmail Draft 的运行时权威与记录：Audit SPEC、Monthly Authority、Handoff Schema、Monthly Final、Monthly Handoff、Daily Ledger，以及职责范围内需要读取的 Governance artifact。此规则不扩大各消费者的 Authority 边界；晨报仍不读取 Monthly Authority / Handoff Schema 作为自身方法或运行补救。

1. 普通 Gmail message search 仅是发现入口。返回 0 条、索引延迟或搜索失败均不能证明 Draft 不存在；在作出缺失、unavailable 或允许创建的判断前，必须调用 Draft list/native retrieval 再核验。优先直接采用 Draft-native 路径。
2. Draft list 必须沿 next_page_token 遍历到分页结束，再在本地按目标命名空间、精确 Subject 与正文元数据筛选。不得把单页、snippet、工具输出截断或搜索摘要当作完整结果。列表返回 draft_id 与 message_id 时分别保存，不得混用；以 message_id 读取完整 MIME 正文是有效的 list→read 路径。已有可靠 ID 可直接读取，但不能据此证明无其他候选或无重复。
3. 合并各检索路径的候选，按底层 Draft / message 身份去重；同一对象被多路径命中不计为重复，不同对象即使正文一致也不能擅自合并。读取目标候选完整正文，核对实际 Subject、业务 STATUS、版本、EFFECTIVE_FROM / VALID_FROM 与 SUPERSEDES。Gmail DRAFT 标签不等于正文业务 DRAFT；高版本业务 DRAFT 不能屏蔽已生效 FROZEN 版本。
4. 若尚无可用候选或无法完成必要的唯一性核验，必须尝试当前实际可用的其他 Draft-native 路径；不能臆造不可调用接口。只有所有可用 Draft 检索路径均已失败或无可用候选，才可报告检索意义的 unavailable。区分：完整列举后确无候选、候选未生效/结构无效、读取/权限失败、分页不完整；不得把后几类描述为制品不存在。已有候选冲突按原 DUPLICATE / AMBIGUOUS 规则处理，不得伪装成缺失。版本链校验失败仍适用原失败规则，并明确原因。
5. 运行前固定任务开始时间 T；生效选择沿用本制品原有规则。FULL 独立执行，DELTA 依链解析；历史记录按自身版本解释。当前研究状态仍由有效 Handoff + replay boundary 后截至 T 的 Daily Events 重建，不因检索修复改变 SNAPSHOT_CUTOFF。
6. Daily duplicate check 的零结果必须来自已完成的 Draft-native 全部分页及精确实际 Subject 核验。普通搜索 0 条、权限错误、分页中断或相关候选读不全均不是“0封”。查重不确定时禁止创建，报告查重未完成并保留原因；不得借 unavailable 推导出允许写入。发现 1 封则 ALREADY_EXISTS，多于 1 封则 DUPLICATE；均不得覆盖、合并、删除或补写历史。创建前再次核验当日 Subject；写入响应不明确时先 native 检索和回读，禁止盲目重试造成重复。
7. 仅在各制品既有写入条件全部满足时写入；写后通过 Draft list→完整正文回读核验 Subject、版本、状态与内容，不把工具返回成功当作唯一持久化证据。读取失败不得阻断晨报完整正文；审计状态必须如实报告。此协议不授权修改、发送或删除历史对象。
8. 执行时保留简短检索诊断：使用过的路径、分页是否结束、候选数量、失败原因及最终选择；不为检索诊断新建 Daily Event，不建立额外永久登记簿。
