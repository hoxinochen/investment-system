SPEC_NAME: Investment Morning Report Audit Ledger  
SPEC_VERSION: 1.0  
STATUS: FROZEN  
EFFECTIVE_FROM: 2026-08-18  
RETENTION_POLICY: PERMANENT  
AUTHORITY_ROLE: Protocol Authority  
  
==================================================  
1. PURPOSE  
==================================================  
本规范定义投资晨报 Daily Audit Ledger 的持久化、事件分类、幂等、不可变性、评价预注册、读取与长期保留规则。  
  
核心原则：  
Memory != Audit Log  
Conversation History != Authority  
Prediction creation 与 Prediction evaluation 永远分离。  
旧记录不覆盖，新认识通过追加新事件表达。  
Forecast、Baseline、Hypothesis、Method Change 分账管理。  
  
Gmail Draft 仅保存“我们当时正式形成了什么判断”。真实世界后来发生了什么，必须由国家统计局、央行、Fed、BLS、交易所、公司公告与财报、市场原始数据等 Reality Authority 验证。Monthly Review 负责 Evaluation Authority。  
  
==================================================  
2. STORAGE LAYER AND SUBJECT  
==================================================  
Daily Audit Ledger 使用 Gmail Draft 持久化，不发送邮件。  
  
正式 Daily Ledger Subject：  
[INV-AUDIT][DAILY] YYYY-MM-DD  
  
每个自然日最多一封正式 Daily Ledger。  
禁止维护单一月度大 Draft 并持续覆盖。  
  
SPEC Subject：  
[INV-AUDIT][SPEC] Audit Ledger v1.0  
  
本 SPEC 一旦冻结，后续 Task 只能 READ，不得 UPDATE、SEND、DELETE、REPLACE。未来升级必须新建 v1.1、v2.0 等新 SPEC；旧 SPEC 永久保留。  
  
==================================================  
3. EVENT-DRIVEN, NOT CHECK-IN  
==================================================  
Daily Audit Ledger 是事件日志，不是签到记录。  
  
只有当日存在至少一种正式审计事件时才创建 Daily Draft：  
- BASELINE_CHANGED  
- BASELINE_CONFIDENCE_CHANGED  
- FORECAST_CREATED  
- FORECAST_CONFIDENCE_CHANGED  
- HYPOTHESIS_CREATED / HYPOTHESIS_STATUS_CHANGED（如确有新事件）  
- METHOD_CHANGED  
  
如果当天仅重复既有判断、没有宏观基线变化、没有新的正式方向性预测、只是普通新闻/数据更新，则不创建 Ledger。  
禁止为了“一天一封”创建 NO_CHANGE / NO_AUDITABLE_JUDGMENT 记录。  
  
==================================================  
4. IMMUTABILITY / WRITE-ONCE-READ-MANY  
==================================================  
任何 [INV-AUDIT][DAILY] Draft 创建成功后，所有投资晨报与月报 Scheduled Task 均必须把它视为 immutable。  
  
允许：  
- READ  
- SEARCH  
  
禁止：  
- UPDATE  
- SEND  
- DELETE  
- REPLACE  
- 以新内容覆盖旧记录  
  
如果旧判断发生变化，只能创建新的追加事件并引用旧 ID；不得修改原 Daily Draft。  
  
如果发现历史记录存在事实错误，必须通过后续 CORRECTION / EVALUATION 事件表达，不得回写原记录。  
  
==================================================  
5. IDEMPOTENCY  
==================================================  
创建当日 Ledger 前，必须先精确搜索：  
in:drafts subject:"[INV-AUDIT][DAILY] YYYY-MM-DD"  
  
若同日正式 Daily Ledger 已存在：  
- 不得修改；  
- 不得创建第二封同日正式 Ledger；  
- 本次运行将持久化状态记为 AUDIT_LEDGER_ALREADY_EXISTS；  
- 晨报正文仍正常输出。  
  
如果发现同日期存在多封正式 Daily Ledger，视为审计异常，后续 Monthly Review 必须明确报告 DUPLICATE_LEDGER，不得静默选择其一。  
  
==================================================  
6. TIME AUTHORITY  
==================================================  
Gmail UI 时间、Draft MIME Date、最近自动保存时间不得作为 Prediction Creation Time 的唯一 Authority，因为 Draft 元数据可能因保存/刷新而变化。  
  
Daily Ledger 正文必须包含：  
SCHEMA_VERSION: 1.0  
SPEC_VERSION: Audit Ledger v1.0  
EVENT_DATE: YYYY-MM-DD  
TASK_SCHEDULED_FOR: YYYY-MM-DDT08:00:00+08:00  
LEDGER_CREATED_AT: 当前实际 Asia/Shanghai 时间（仅在可可靠取得时填写；不可可靠取得时不得猜测，可写 UNKNOWN）  
  
EVENT_DATE 表示该判断属于哪一期晨报，是主要逻辑日期。  
TASK_SCHEDULED_FOR 表示任务计划执行时间。  
LEDGER_CREATED_AT 仅作为辅助执行时间，不以 Gmail UI 时间替代。  
  
分钟级调度延迟本身不改变 EVENT_DATE；真正需要防止的是事后数小时或数天补写预测。  
  
==================================================  
7. RECORD TYPES  
==================================================  
A. BASELINE  
描述当前世界状态，不进入 Forecast Scoreboard。  
  
BASELINE_CHANGED 必须记录：  
domain  
previous  
current  
confidence  
triggers  
  
如果只是证据加强/削弱旧判断而世界模型没有改变，必须使用 BASELINE_CONFIDENCE_CHANGED，不得伪装成 BASELINE_CHANGED。  
  
B. FORECAST  
只有同时满足以下条件，才允许进入 Forecast Scoreboard：  
- 明确判断对象  
- 明确方向  
- 明确时间尺度  
- 明确置信度  
- 明确 validation  
- 明确 invalidation  
- 明确 evaluation_window  
- 预先冻结 evaluation_rule  
  
不能满足上述条件的倾向、评论、情景讨论，不得为了增加样本数强行登记为 Forecast。  
  
C. HYPOTHESIS  
待验证解释框架，不计入预测正确率。  
状态可使用：OPEN / CONFIRMED / STRENGTHENED / WEAKENED / REJECTED。  
  
D. METHOD_CHANGE  
记录分析方法本身的重要改变，进入 Methodology / Decision Log，不进入 Forecast Scoreboard。  
  
==================================================  
8. FORECAST ID AND LIFECYCLE v1  
==================================================  
Forecast ID 必须长期唯一。  
格式：YYYYMMDD-DOMAIN-序号  
示例：20260818-GOLD-01  
  
v1 正式支持：  
- FORECAST_CREATED  
- FORECAST_CONFIDENCE_CHANGED  
- FORECAST_EVALUATED（由 Monthly Review 提议/形成）  
  
置信度改变必须引用原 Forecast ID，并保留 previous_confidence / current_confidence / reason。  
不得创建一个新 Forecast 来偷偷替代旧 Forecast。  
  
SUPERSEDED / INVALIDATED / EXTENDED 等复杂生命周期事件暂留 v1.1，除非后续真实案例证明必须提前加入。  
  
==================================================  
9. FORECAST PRE-REGISTRATION  
==================================================  
FORECAST_CREATED 至少包含：  
  
EVENT: FORECAST_CREATED  
ID: YYYYMMDD-DOMAIN-01  
date: YYYY-MM-DD  
domain: ...  
horizon: 1W / 1-3M / other explicit window  
judgment: ...  
direction: ...  
confidence: HIGH / MEDIUM / LOW 或与晨报等价的明确等级  
validation:  
- ...  
invalidation:  
- ...  
evaluation_window: start -> end  
evaluation_rule: ...  
  
Evaluation Rule 必须在创建当天冻结，不得月底看完结果再重新定义“什么算正确”。  
  
评价规则应尽量机械、可复核。若规则仍含主观判断，必须明确列出判断维度，至少包括方向结果、主要驱动是否成立、是否触发 invalidation、是否存在明显 timing/magnitude 偏差。

==================================================  
11. MORNING REPORT RELATIONSHIP  
==================================================  
投资晨报正文负责：  
- 新闻与数据  
- 宏观解释  
- 市场分析  
- 资产映射  
- 预测逻辑  
- 今日观察事项  
  
Daily Audit Ledger 仅负责抽取：  
“未来值得被追责和验证的正式判断”。  
  
Morning Report Body = 为什么当时这么判断  
Daily Audit Ledger = 当时正式判断了什么  
  
需要深入错误分析时，Monthly Review 可根据 Forecast ID 和 EVENT_DATE 回到相应晨报上下文；晨报正文不是 Prediction Record Authority。  
  
==================================================  
12. WRITE FAILURE ISOLATION  
==================================================  
Audit 持久化失败不得导致晨报正文失败。  
  
正确行为：  
- 晨报照常完成并发布；  
- Draft 创建失败时明确输出 AUDIT_PERSISTENCE_FAILED 及简短原因；  
- 不得声称已保存；  
- 不得通过覆盖历史 Draft 进行补救；  
- 后续是否补录必须按专门 Correction / Recovery 规则并保留实际补录时间，不能伪装成原始当天记录。  
  
==================================================  
13. MONTHLY READ CONTRACT  
==================================================  
Monthly Review 的第一数据源应为上一个完整自然月的所有：  
[INV-AUDIT][DAILY] YYYY-MM-DD  
  
先重建：  
- Forecast List  
- Baseline Timeline  
- Confidence Changes  
- Hypothesis List  
- Method Changes  
  
再读取 Reality Authority 验证真实结果。  
  
Authority 分层：  
Prediction Record Authority = Daily Gmail Draft  
Reality Authority = 官方统计、央行、交易所、公司财报及其他权威原始数据  
Evaluation Authority = Monthly Review / 经用户确认后的正式月度评价  
  
三层不得混淆。  
  
==================================================  
14. EVALUATION APPEND-ONLY  
==================================================  
历史 Forecast 的评价不得修改原 Daily Ledger。  
  
允许结果：  
- CORRECT  
- PARTIAL_TIMING_OR_MAGNITUDE  
- WRONG_DIRECTION  
- NOT_YET_VERIFIABLE  
  
错误类型至少考虑：  
- DATA_ERROR  
- TRANSMISSION_ERROR  
- TIMING_ERROR  
- MAGNITUDE_ERROR  
- OMITTED_VARIABLE  
- POLICY_REACTION_ERROR  
- MARKET_FUNDAMENTAL_DECOUPLING  
- UNPREDICTABLE_EVENT  
  
不得用“受到突发事件影响”作为完整错误归因。  
即使事件不可预测，也要检查当时是否本应提高该风险权重。  
  
==================================================  
15. RETENTION AND MIGRATION  
==================================================  
正式 SPEC：PERMANENT  
正式 DAILY_LEDGER：PERMANENT  
未来 MONTHLY_FINAL：PERMANENT  
测试 Draft：可在确认测试完成后人工删除  
自动删除：PROHIBITED  
自动清理：PROHIBITED  
  
不得为了邮箱整洁删除正式 Audit Authority。  
如果未来 Gmail 不再适合作为 Authority，应执行：  
迁移 -> 数量/ID/内容完整性校验 -> 新 Authority 生效 -> 用户明确批准 -> 才允许退役旧存储。  
  
删除机制不是默认生命周期；迁移机制才是。  
  
==================================================  
16. SCHEMA EVOLUTION  
==================================================  
本 SPEC v1.0 冻结后不得修改。  
未来任何规则变化均通过新 SPEC 表达，例如：  
[INV-AUDIT][SPEC] Audit Ledger v1.1  
  
新版本必须注明：  
STATUS  
EFFECTIVE_FROM  
SUPERSEDES  
主要变更  
  
每份 Daily Ledger 必须明确 SPEC_VERSION，使未来能够解释历史记录究竟按哪一版规则生成。  
  
==================================================  
17. FINAL PRINCIPLE  
==================================================  
系统目标不是提高表面预测胜率，而是长期识别：  
- 哪类判断最可靠  
- 哪类判断经常过早  
- 哪些高置信度判断实际上不稳定  
- 哪些传导链理解错误  
- 哪些来源和信号应升权或降权  
- 晨报的方法论应如何持续进化  
  
本 SPEC 自 2026-08-18 起作为 Audit Ledger v1.0 Protocol Authority。
